IronClaw — 一个常驻、自我扩展、纵深防御的
个人 AI 智能体

如果说 Claude Code 是「终端里的编码智能体」，那么 IronClaw 是把同一套「LLM 推理 → 工具调用 → 观察 → 再推理」的智能体内核，长成一个 7×24 在线、多渠道接入、能自己造工具、把不可信代码关进沙箱的私人助理服务。本页基于真实代码梳理， 并对每个子系统给出 ✓/⚠/✗ 三档评级。

Rust 2024 · v0.28 30 个 workspace crate tokio 全异步 WASM 沙箱 (wasmtime) PostgreSQL + libSQL 双后端 Engine v2 / CodeAct MCP 协议

◆核心信条（来自 README 与 CLAUDE.md）

用户优先

数据全部本地存储、加密、绝不外泄；无遥测。「你的 AI 应当为你工作」。

纵深防御

不可信工具进 WASM 沙箱；凭证零暴露；提示注入多层拦截。

自我扩展

描述需求 → 智能体现场编译出新的 WASM 工具；可接 MCP 生态。

主动执行

Heartbeat 心跳 + Routines 定时/事件触发，后台自主干活，而非纯被动应答。

◆如何阅读本文档的「完善度」标记

✓ 生产级 · 实现完整

关键类型/函数已逐项定位、无桩标记、被运行时实际调用。可放心依赖。

⚠ 部分 / 实验

主干可用但有明确、具名的缺口（如 opt-in 默认关闭、缺渐进式 streaming、效果待经验验证）。

✗ 桩 / 缺失

占位代码、仅有设计、或文件不存在。

⚠ 评级是「代码实现的完成度」，不等于「已在大规模生产环境验证」。 每节标题右侧的 ✓/⚠ 徽章只作粗略指示；第 14 节是逐项实证总表，每条都附原始 grep / GitHub issue 证据——精确判断以第 14 节为准。

⚠ 阅读本图前必须理解的一件事：代码库正处于「三态并存」的迁移期

仓库里同时存在三套结构，本文档会分别标注它们：

① Legacy v1（src/agent/）— 最初的单体 Agent 事件循环，目前默认运行。

② Reborn 分层 crate（crates/ironclaw_*，30 个）— 把宿主能力按「权威 → 基础设施 → 调度 → 运行时」重新解耦的新地基。

③ Engine v2（crates/ironclaw_engine/）— 用 5 个原语 + Python 编排器（CodeAct）重写的统一执行引擎，靠 ENGINE_V2=true 开启（opt-in，非默认）。

src/bridge/ 是把 v1 渠道层接到 v2 引擎的适配桥。理解架构 = 理解这三者各管什么、如何拼接。

03一条消息的完整生命周期

以「用户在 Telegram 发一句话」为例，追踪它如何穿过整个系统并返回。这是理解全局的最快路径。

1
外部事件抵达

Telegram Webhook POST → 统一 HTTP 服务器验签（HMAC / Ed25519）→ 分发给 telegram.wasm 的 on_http_req() 回调。

src/channels/webhook_server.rs · src/channels/wasm/router.rs
2
WASM 渠道解析并 emit

WASM 模块解析 JSON，调用宿主导入 emit_message(sender_id, content)。宿主做配对校验（陌生人需 pairing 批准）+ 限流，构造 IncomingMessage。

src/channels/wasm/host.rs · src/pairing/
3
ChannelManager 流合并

所有渠道的 MessageStream + 内部注入通道经 futures::select_all 合并为单一流，被 Agent::run() 轮询。

src/channels/manager.rs
4
解析与路由

SubmissionParser 区分 /命令、审批应答、自然语言；AuthManager 解析 extension_name vs credential_name。然后分叉：v1 走 SessionManager，v2 走 bridge::router。

src/agent/submission.rs · src/bridge/router.rs
5
智能体循环（ReAct）

进入 run_agentic_loop()（v1）或 ExecutionLoop::run()（v2）：检查信号 → 装配上下文 → 调用 LLM → 若返回文本则结束，若返回工具调用则执行 → 回灌结果 → 重复（上限约 50 轮）。

src/agent/agentic_loop.rs · crates/ironclaw_engine/src/executor/loop_engine.rs
6
工具执行 + 安全管线

每个工具调用经 SafetyLayer（注入检测 → schema 校验 → 参数脱敏）→ 经 ToolRegistry 派发到 Builtin / WASM / MCP；高危工具触发审批门。结果包进 <tool_output> 再回灌。

src/tools/dispatch.rs · crates/ironclaw_safety/
7
响应回流

最终文本经 LeakDetector 出站扫描 → ChannelManager::respond() 按 msg.channel 路由回 Telegram WASM 的 on_respond() → 调 Telegram API；Web 端则把过程事件投影成 AppEvent 经 SSE/WS 实时推送。

src/channels/manager.rs · src/channels/web/platform/sse.rs
关键不变量 · 多租户隔离

SSE/WS 订阅按 bearer token 推导的 user_id 作用域；消息 metadata.user_id 始终被真实 user_id 覆盖，调用方无法伪造跨租户访问。

04Channels / I-O 表面✓

这是 IronClaw 区别于 Claude Code 最大的地方：不是单一终端，而是一个可插拔的多渠道接入层。 所有渠道实现同一个 Channel trait，于是「换渠道」对智能体核心完全透明。

▸Channel trait — 统一抽象

核心方法

start() → MessageStream 启动并产出消息流

respond(msg, resp) 同步回复原始消息

broadcast(user_id, resp) 主动推送（无需关联）

send_status(status, meta) 实时状态指示

src/channels/channel.rs

ChannelManager

用 select_all 把所有渠道流合并成一条；hot_add() 支持运行时热替换渠道。

注入通道：后台任务（Job 监控、调度器）可经 mpsc 把 IncomingMessage 注入主流，无需实现完整 Channel。

src/channels/manager.rs

▸四类渠道实现 — 各自成熟度

REPL / TUI ✓

终端交互。TUI 用 Ratatui 构建（ironclaw_tui crate），多会话面板。

HTTP Webhook ✓

HttpChannel，HMAC-SHA256 验签，60 req/min 限流，可选同步响应关联。

WASM Channels ⚠

5 个渠道是预编译 WASM；激活路径（boot + hot-activation）已实现，但有一组未关闭的精修 bug：hook 生命周期绑定 (#2558)、scope 模型 (#2564)、多租户出站 (#2263)。

Web Gateway ✓

浏览器 SPA，SSE + WS 双流，11 个 feature 切片，约 9.5k LOC。

▸WASM Channel 模型 — 宿主托管事件循环（NEAR 模式）

渠道不是常驻进程，而是每次回调创建全新实例，无共享可变状态。宿主（Rust）负责 HTTP 路由、轮询循环、定时器；WASM 只定义行为回调。

WASM Channel — host ⇄ guest 边界
宿主托管HTTP router · poll loop · timer
⇄
WASM 导出回调on_http_req · on_poll · on_respond
⇄
宿主导入emit_message · http_request · get_config · log

凭证从不进入 WASM：WASM 调 http_request 时，宿主在边界处注入解密后的认证头；get_config(key) 读到的是宿主从加密 secrets store 解出的值。

▸Web Gateway · Tunnel · Pairing

Auth Gate（v2 路径）

工具需 OAuth 凭证时，引擎抛出 Authentication 门 → gate_controller 暂停 VM → SSE 广播 GateRequired → 用户点「连接」→ /api/chat/gate/resolve → 引擎恢复重试。

Tunnel 抽象 ✓

Tunnel trait：cloudflare / tailscale / ngrok / custom / none 五个 provider 全实现。把本地 8080 暴露成公网 URL。

Pairing 配对

陌生人首次 DM → 返回配对码 → 用户在 Web UI 批准 → PairingStore 记录 (channel, external_id, owner)。DM 默认门禁。

▸主动性 · 上下文管理

Heartbeat 心跳 ✓

默认每 30 分钟（或固定时刻）：读 workspace 里的 HEARTBEAT.md 清单 → 跑一轮智能体 → 有发现才经渠道通知，否则静默回 HEARTBEAT_OK。支持静默时段、多租户轮询。已知缺口：进程重启后区间计时不恢复。

src/agent/heartbeat.rs

Compaction 压缩

Token 用量逼近上限（默认 100k 的 80%）时三策略：80–85% 转存 workspace、85–95% LLM 摘要、>95% 直接截断旧 Turn。LLM 数据永不删除，只归档。

src/agent/compaction.rs

06Engine v2 与 CodeAct 范式✓

v2 是对 v1 的彻底重构：用 5 个原语替代约 10 个旧抽象，并把循环编排逻辑从 Rust 下放到一个可自我修改的 Python 编排器。靠 ENGINE_V2=true 开启 —— 代码完整、约 38.6k LOC、527 测试，但目前 opt-in、非默认。

▸能力租约 — 没有静态权限，只有动态租约

🔑 Capability Lease ✓

Thread 不持有静态权限。它领取有作用域、有时限、有次数上限的租约：CapabilityLease { thread_id, capability_name, granted_actions, expires_at, max_uses, revoked }。

PolicyEngine 确定性裁决：Deny > RequireApproval > Allow。动作按效应分类：ReadLocal / ReadExternal / WriteLocal / WriteExternal / CredentialedNetwork / Compute / Financial。

07工具系统 — 一切行动都经过工具✓

三种执行模型（原生 Rust / 沙箱 WASM / 远程 MCP）统一在一个 Tool trait 之后。 核心铁律：所有非智能体调用方（网关、CLI、Routine、WASM 渠道）必须经 ToolDispatcher::dispatch()，绝不直接碰 DB / workspace。

▸ToolDispatcher — 唯一的中枢咽喉

为什么强制单一入口？因为每个 UI 发起的变更都应继承与智能体发起的工具调用同样的： 审计轨迹（ActionRecord）、安全管线（参数校验、敏感参数脱敏、输出消毒）、渠道无关性。 scripts/pre-commit-safety.sh 会标记 handler/CLI 文件里新增的直接 state.store.* 访问。

08Skills 架构 — 是的，有完整的技能系统✓

直接回答常见疑问：IronClaw 有完整的 Skills 架构，理念与 Claude Code 的 Skills 高度相似—— SKILL.md 文件（YAML frontmatter + markdown 正文）把领域知识注入 LLM 上下文。专属 crate ironclaw_skills/ 约 6.5k LOC，仓库根 skills/ 目录有 31 个真实技能。

09多智能体 · lead-sub · agent-as-tools⚠

这一节回答两个常被混为一谈的问题：① 有没有「lead 协调器」？② 支不支持「agent-as-tools」？ 二者正交——下面先把它们拆开，再与 OpenAI Agents SDK 横向对照。

▸先拆概念 — 两件不同的事

概念 A · 「lead 协调器」由谁扮演

问的是：有没有专门的编排大脑
  • 没有名为 LeadAgent / Coordinator 的结构体
  • 每个 Thread 就是普通单智能体主循环 ExecutionLoop
  • 父 Thread 的循环顺带决定「派生什么子任务」——lead 角色被普通主循环隐式兼任
  • 这只说明「缺一个显式协调器」，不构成 agent-as-tools 的证据

概念 B · 「agent-as-tools」支不支持

问的是：能不能把子智能体当可调用的东西
  • 支持——靠 create_job 与 llm_query 两个机制
  • 结构骨架是 ThreadTree（runtime/tree.rs，维护父子映射）；线程事件经 EventKind 枚举（types/event.rs）
  • 与「谁当 lead」无关，是另一套独立能力
  • 两机制各占「完整 / 同步」光谱的一半（见下表）

▸横向对照 · OpenAI Agents SDK

这个 create_job + llm_query 的模式，精神上接近 OpenAI Agents SDK 的核心理念 「Agent = LLM + tools + instructions，且 tool 可以是另一个 Agent」，但架构落点不同。

⚠ 核心洞察 · 那块缺失的拼图

OpenAI Agents SDK 好用的本质，是它的 agent-as-tool 同时满足「同步 + 完整循环」——把子 agent 放进工具栏， 调用它就像调普通函数，跑完拿结果继续推理。

IronClaw 的两个机制各占一半：llm_query 同步但非完整循环；create_job 完整循环但异步。 「同步 + 完整循环」那个交集——「调一个完整子 agent、阻塞等它、把最终答案拿回来继续」——目前没有对应原语。

底层 ThreadManager::spawn_thread() 有能力支撑它；缺的是在 CodeAct 暴露一个 await run_agent(task, tools=[...]) 宿主函数。补上它，IronClaw 才真正对齐 OpenAI Agents SDK 的 agent-as-tool 体验。

把 IronClaw 的多智能体模型整体对标一个框架，不是单一的 OpenAI Agents SDK，而是三者叠加：

⚠ 专业评判 · 站在 staff engineer 视角，这个闭环到底成熟到什么程度？

代码层面 — 真实、完整、有测试。不是 vaporware，也不是 scaffolding：MissionManager 约 8.5k LOC， 4 个 mission 全部接线，事件驱动监听 ThreadOutcome::Completed，5 个 prompt/mission_*.md 模板齐全， ironclaw_engine 整体 527 个测试。把它当「已落地的能力」看是公允的。

但有三点必须诚实说明，所以整体给 ⚠ 而非 ✓：

① 「实现且测试通过」≠「能让 agent 可度量地变好」。自我改进的有效性是经验问题—— 需要纵向指标证明 agent 真的随时间变强。代码审计能证明「闭环会运转」，无法证明「闭环有正收益」。

② 真正自主的只有 L1 / L2（提示叠加、编排器补丁）；L3（改 Rust）人工把关。 所以「自我修改」是有边界的——这是好的安全设计，但也意味着别把它想象成无限自我重写。

③ 整条闭环只在 ENGINE_V2=true 下运行，而 v2 目前 opt-in、非默认。今天绝大多数用户其实拿不到它。

▸横向类比 · 自我进化闭环 vs Claude Code

Claude Code

人工策划 · 无自演化 — 是有意的保守
  • CLAUDE.md — 人工写的记忆/规则，不自动生长
  • Skills — 人工撰写或安装，不从轨迹自抽
  • Hooks — 人工配置的生命周期钩子
  • 不会诊断自己的失败并改自己的编排逻辑
  • 优点：行为可预测、无能力漂移、易审计

IronClaw Engine v2

事件驱动自演化 — 设计明显更激进
  • 4 个学习任务从自己的执行轨迹学习
  • skill-extraction 自动抽取新技能（带可执行代码）
  • self-improvement 自动改提示层 / 编排器代码（L1/L2）
  • skill-repair 版本化修复陈旧技能、可回滚
  • 代价：需要 metrics/置信度系统防止低质技能堆积；效果待经验验证；仅 v2 可用

一句话：在「自我进化」这一维，IronClaw 是真投入了工程、做出了 Claude Code 刻意没做的东西—— 但「更激进」不等于「更好」。Claude Code 的「不自演化」是为可预测性付的费；IronClaw 的闭环是为适应性下的注， 注是否赢，要看 metrics，而不是看代码行数。

15对照 Claude Code

两者共享同一个智能体内核思想，但定位不同：Claude Code 是「开发者的终端编码助理」， IronClaw 是「把这套内核长成 7×24 个人助理服务」。下表逐维度对照。

形态CLI / IDE 扩展，开发者交互式驱动常驻服务，多渠道接入（Telegram/Slack/Web/Webhook）

一句话总结

IronClaw ≈ 「Claude Code 的智能体内核」 + 「多渠道服务化外壳」 + 「WASM/Docker 双沙箱安全地基」 + 「持久记忆与自我进化闭环」， 用 Rust 重写以获得原生性能、内存安全与单二进制部署。源出 OpenClaw（TypeScript），见 FEATURE_PARITY.md。 它在安全与持久化上比 Claude Code 走得更远更扎实；在自我进化上比 Claude Code 更激进—— 但「更激进」是一个尚未被 metrics 证实的赌注，而非已兑现的优势。
